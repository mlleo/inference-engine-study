1. BASIC KV CACHE FORMAT CONVERSION LAYER
- H100 (FlashAttention) produces KV cache in layout A
- MI300X (ROCm attention) expects layout B
- Write a conversion function: rearrange tensor strides, head ordering, padding
- Success condition : decode on MI300X produces correct tokens

2. KV CACHE TRANSFER PIPELINE
- Transfer KV cache from H100 node to MI300X node over network/RDMA
- Overlap transfer with prefill computation to hide latency
- Standard systems engineering — RDMA, memory buffers, async copy
- Success condition : transfer latency < prefill time (hidden)

3. STATIC RESOURCE ALLOCATION
- Given your workload profile, assign H100s to prefill pool, MI300Xs to decode pool at a fixed ratio
- Success condition : throughput improves vs homogeneous baseline

4. END-TO-END CORRECTNESS VERIFICATION
- Run model end-to-end across vendors
- Verify outputs match within tolerance
- Standard testing
- Success condition : Outputs are correct

Research

Idea 1. Adaptive prefill / decode allocation

Problem : "Always H100=prefill, MI300X=decode" is not optimal. The allocation of H100 and MI300X instances to prefill and decode pools should adapt based on below factors.

Factor 1. Workload type
- Decode-heavy (chatbot, coding): MI300Xs saturated, H100s idle
- Prefill-heavy (RAG, summarization): H100s saturated, MI300Xs idle
- Mixed: need dynamic rebalance

Factor 2. QUEUEING STATUS (real-time)
- Even for the same workload type, queue lengths change in real-time
- If prefill queue on H100 is long but MI300X decode queue is empty -> should some MI300Xs run prefill? (slower but reduces H100 queue)
- If decode queue on MI300X is long but H100 prefill queue is empty -> should some H100s run decode? (wastes compute but clears queue)


Factor 1. Workload-Driven Cross-Vendor Phase Imbalance 
- Input/output token length distribution 
- Prefill-to-decode demand ratio under TTFT/TPOT SLOs 
- Request arrival rate and burstiness 
- H100/MI300X phase-specific throughput and cost asymmetry 
- Prefix-cache reuse and KV-cache footprint 
Naive solution: Estimate the workload’s prefill/decode pressure and statically reserve more H100s for prefill-heavy periods and more MI300Xs for decode-heavy periods, while keeping a small flexible pool for imbalance.

Factor 2. Runtime Cross-Vendor Deflection Tradeoff 
- Current prefill/decode queueing delay on each vendor pool 
- Per-request TTFT/TPOT slack 
- Expected service-time gap between default and deflected vendors 
- Cross-vendor penalty: KV transfer, cache miss, format conversion, network cost 
- H100 opportunity cost and future phase-starvation risk 
Naive solution: Deflect prefill to MI300X or decode to H100 only when the estimated SLO benefit exceeds the service-time penalty, cross-vendor overhead, and H100 opportunity cost.

GOAL: Minimize H100 count while meeting SLO, given MI300X pool and dynamic workload.

Reference
1. Kairos (https://arxiv.org/pdf/2605.02329)
- SLO-aware scheduling for disaggregated serving
- Prefill side: urgency-based priority scheduling (predicts prefill completion times, selects requests to maximize TTFT SLO)
- Decode side: slack-guided adaptive batching (uses gap between per-step decode time and TPOT SLO to pack more requests)
- Result: 23.9% TTFT SLO improvement, 27.1% TPOT SLO improvement
- RELEVANCE: Good baseline for SLO-aware scheduling. But assumes homogeneous GPUs. Cross-vendor adds: which vendor to schedule on, not just when to schedule.

2. NetKV (https://arxiv.org/pdf/2606.03910)
- Network-aware decode instance selection
- Key insight: ignoring network topology makes scheduling arbitrarily suboptimal as context grows
- O(|D|) greedy algorithm with provable robustness to stale telemetry
- Result: 21.2% mean TTFT reduction
- RELEVANCE: Cross-vendor transfer has HIGHER network cost (different nodes, potentially different network paths). The network-aware selection is even more critical cross-vendor.

3. HexAGent (https://arxiv.org/pdf/2605.16637)
- Workflow-aware scheduling for heterogeneous GPU clusters (A100/H100/H200)
- Models each request as online-revealed DAG, jointly selects prefill placement, decode placement, and queue priority
- Result: 20-33% SLO scale reduction
- RELEVANCE: Closest to heterogeneous GPU scheduling. But all NVIDIA GPUs. Cross-vendor adds: KV cache format conversion cost, numerical divergence, different software stacks. The placement decision is not just about compute/memory but also about vendor boundary crossing cost.

4. ConServe (https://arxiv.org/pdf/2410.01228)
- Conversation-level disaggregated scheduling for agentic workloads
- Key insight: raise scheduling unit from turn to conversation
- Maps two phases onto heterogeneous GPU tiers for 22.75% energy efficiency gain
- RELEVANCE: Shows that heterogeneous GPU tiers help. But doesn't address cross-vendor or dynamic reallocation.

5. HMA-Serve (https://arxiv.org/pdf/2606.29986)
- Cross-vendor disaggregated serving! Pairs GDDR-based accelerators for prefill with HBM-based GPUs for decode
- Uses phase-wise quantization, compute-transfer pipeline, deferred dequantization
- Result: 3.2x goodput, 4.8x goodput-per-dollar
- RELEVANCE: This is the closest prior work to your idea. It proves cross-vendor disaggregation works.
- Limitations : It uses GDDR accelerators (not H100) for prefill, It focuses on system design, NOT adaptive scheduling, Static allocation (GDDR=prefill, HBM=decode always), Does NOT study when to deflect prefill to HBM or decode to GDDR, Does NOT study workload-dependent or queue-dependent allocation, Does NOT use SGLang or address RadixAttention

6. Prefill Deflection (https://arxiv.org/pdf/2607.02043)
- Load-aware prefill deflection scheduler for disaggregated LLM serving
- Key insight: prefill execution is only 2-23% of P95 TTFT; queuing and KV cache transfer dominate the rest
- Lets decode nodes serve prefill as chunked-prefill steps interleaved with in-flight decode batches, eliminating inter-node KV transfer for deflected requests
- For each queued request, estimates TTFT on prefill node vs decode node, deflects when decode path gives lower TTFT
- Result: 81% P95 TTFT reduction, 79% SLO attainment improvement
- RELEVANCE: Directly addresses the "when to deflect prefill to decode nodes" question. But assumes homogeneous GPUs (all A100). Cross-vendor adds: deflecting prefill to MI300X is slower compute (1307 vs 1979 TFLOPS), deflecting decode to H100 wastes expensive compute with lower bandwidth (3350 vs 5300 GB/s). The cost asymmetry between vendors makes the deflection decision fundamentally harder than same-vendor.


THE RESEARCH Possibility
- HMA-Serve proves cross-vendor disaggregation works at the system level. Prefill Deflection shows dynamic prefill/decode reallocation helps. But NOBODY has combined them:
- Cross-vendor + adaptive scheduling: when should H100 handle decode or MI300X handle prefill, given vendor asymmetry AND queue state?
- The cost model is fundamentally different from same-vendor: 
  - Deflecting prefill to MI300X: slower compute (1307 vs 1979 TFLOPS)
  - Deflecting decode to H100: wastes expensive compute, lower bandwidth (3350 vs 5300 GB/s)
  - The cost asymmetry between vendors makes the deflection decision harder than same-vendor

Research questions
- Given workload type and real-time queue state on both H100 and MI300X pools, what is the optimal allocation to minimize H100 usage while meeting SLO?
- When should prefill be deflected to MI300X (slower but frees H100)? What is the queue length threshold?
- When should decode be deflected to H100 (wastes compute but clears MI300X queue)? What is the queue length threshold?
- How does the cost asymmetry (H100 is 2-3x more expensive than MI300X) change the deflection decision vs same-vendor?
- How to manage SGLang RadixAttention prefix cache when prefill and decode may run on either vendor dynamically?
- What is the theoretical minimum H100 count for a given workload distribution and MI300X pool size?


Idea 2. Cross-vendor Speculative Decoding

Problem: In standard disaggregated serving, H100 does prefill, then MI300X does decode sequentially — one token at a time. But H100 has massive compute (1979 TFLOPS) that sits IDLE during decode phase. What if H100 generates draft tokens speculatively (fast, using its compute advantage), and MI300X verifies them in parallel (using its memory bandwidth advantage for parallel attention)? This turns vendor asymmetry from a CHALLENGE into an ADVANTAGE.

GOAL: Reduce H100 usage by making each H100 handle more requests through speculative drafting, while MI300X handles verification + decode. Fewer H100s serve the same workload because each H100 spends less time per request (drafts tokens, doesn't do full decode).

Reference
1. SPIN (https://arxiv.org/pdf/2503.15921, INFOCOM 2025)
- Uses multiple heterogeneous draft models (different sizes) for speculative decoding, with learning-based SSM selection
- Pipelines speculation and verification phases on GPUs
- Result: 2.28x performance improvement
- RELEVANCE: Closest to heterogeneous speculative decoding. But "heterogeneous" means different model sizes, not different GPU vendors. Cross-vendor adds: can H100-generated draft tokens be verified efficiently on MI300X with different attention kernels and numerical behavior?

2. DuoDecoding (https://arxiv.org/pdf/2503.00784)
- Deploys draft model on CPU and target model on GPU for parallel execution
- Hardware-aware optimal draft budget to minimize idle time
- Dynamic multi-sequence drafting to enhance draft quality
- Result: 2.61x speedup, TTFT reduced to 83% of conventional speculative decoding
- RELEVANCE: Shows that splitting draft and verify across different hardware works. But CPU-GPU split, not GPU-GPU cross-vendor. Cross-vendor adds: both sides are GPUs but with different architectures, different attention kernels, different numerical behavior — the draft-verify alignment is more complex.

3. Mirror Speculative Decoding (https://arxiv.org/pdf/2510.13161)
- Explicitly maps computation across heterogeneous accelerators (GPU and NPU)
- Draft speculates forward continuations while target simultaneously speculates correction paths — bidirectional speculation
- Speculative streaming: draft emits multiple tokens per step
- Result: 2.8x-5.8x wall-time speedup, 30% improvement over EAGLE3
- RELEVANCE: Closest to cross-vendor speculative decoding! Maps draft and verify across GPU+NPU. But uses NPU (not MI300X GPU), does not address KV cache format mismatch between vendors, does not study numerical divergence impact on acceptance rate, and does not consider SGLang RadixAttention.

4. EAGLE-Pangu (https://arxiv.org/pdf/2603.08088)
- Ports EAGLE-3 tree speculative decoding to Ascend NPUs
- Key finding: tree speculation is "brittle when ported across heterogeneous backends" — attention masking, KV-cache layouts, and indexing semantics are NOT interchangeable across accelerators
- Result: 1.27x average throughput improvement, 2.46x at p99
- RELEVANCE: Directly demonstrates that speculative decoding across different accelerator architectures faces real challenges (KV-cache layout, attention masking). But this is a porting paper (NVIDIA → Ascend NPU), not a study of cross-vendor GPU-to-GPU speculative decoding. Does not study acceptance rate under numerical divergence.

5. Prima.cpp (https://arxiv.org/pdf/2504.08791)
- Distributed inference on consumer home clusters with mixed CPUs/GPUs
- Heterogeneity-aware scheduler (Halda) co-optimizes per-device workloads
- Result: 5-17x lower TPOT vs exo/dllama, 70B at 674ms/token
- RELEVANCE: Shows heterogeneous inference works at consumer scale. But consumer focus (CPU+GPU mix, Wi-Fi), not datacenter cross-vendor GPU. Does not address speculative decoding across vendors or SGLang integration.

6. AHASD (https://arxiv.org/pdf/2604.25326)
- Asynchronous heterogeneous architecture for speculative decoding on mobile (NPU+PIM)
- Task-level DLM-TLM decoupling for parallel drafting and verification
- Entropy-history-aware drafting control to suppress invalid drafting
- Result: 4.2x throughput, 5.6x energy efficiency over GPU-only baseline
- RELEVANCE: Shows heterogeneous speculative decoding works on mobile. But mobile NPU+PIM, not datacenter GPU cross-vendor. Does not address numerical divergence or KV cache format mismatch.

THE RESEARCH POSSIBILITY
- Mirror-SD proves heterogeneous speculative decoding (GPU+NPU) works at the algorithm level. EAGLE-Pangu shows that porting speculative decoding across accelerators is non-trivial (KV-cache layout, attention masking differences). But NOBODY has studied cross-vendor GPU-to-GPU speculative decoding where:
(a) H100 (compute-rich, 1979 TFLOPS) generates draft tokens using its compute advantage
(b) MI300X (memory-rich, 5300 GB/s) verifies multiple tokens in parallel using its bandwidth advantage
(c) The KV cache format and numerical behavior DIFFER between drafter and verifier
- This is fundamentally different from all prior work because:
  - SPIN, DuoDecoding: heterogeneous model sizes or CPU-GPU split, not cross-vendor GPU
  - Mirror-SD: GPU+NPU, but does not study acceptance rate under numerical divergence
  - EAGLE-Pangu: shows porting is hard, but is a porting paper, not a cross-vendor speculative decoding design
  - Nobody studies: does numerical divergence between H100 and MI300X reduce speculative decoding acceptance rate?
- Key unknown: if H100 generates draft tokens with NVIDIA tensor cores and MI300X verifies with AMD matrix cores, the attention scores may differ due to FP accumulation differences. If verification attention scores differ from drafting attention scores, the acceptance rate may drop. This is a new problem that does not exist in any same-vendor or same-architecture speculative decoding system.

Research questions
- Can H100 serve as an efficient draft model generator while MI300X verifies? What is the optimal draft length K given the compute/bandwidth asymmetry?
- Does numerical divergence between H100 and MI300X reduce speculative decoding acceptance rate? By how much?
- How to manage the KV cache when H100 generates drafts and MI300X verifies — does MI300X need to recompute KV for rejected tokens? Or can it reuse H100's KV cache (after format conversion)?
- How does this interact with SGLang RadixAttention? If H100 generates draft tokens, does the prefix cache on H100 help or conflict with MI300X decode cache?
- What is the throughput improvement vs standard cross-vendor disaggregated serving (H100 prefill + MI300X decode without speculation)? How many H100s can be freed?
- Can cross-vendor speculative decoding be combined with adaptive scheduling (Research 1)? When workload is decode-heavy, use H100 for drafting; when prefill-heavy, use H100 for prefill — dynamic role switching.
