배포 방식

전원에게 배포: README.md(개요·규칙·일정), docs/01~05, 코드 전체
개별 배포: docs/workloads/W1~W5.md 중 배정된 것 하나

각 워크로드 카드에는 시나리오, 주 병목, SGLang이 이미 하는 것 / 아직 못 하는 것, 과제 후보 3개(난이도 표시), 스윕할 파라미터, 확인할 서버 로그 항목, 그리고 예상 트레이드오프까지 들어 있습니다. 마지막 항목은 일부러 미리 알려주는 겁니다 — 학생이 5단계에서 뭘 찾아야 하는지 알고 시작해야 합니다.

학생이 첫날 실행하는 명령
bash
bash scripts/setup_pod.sh          # 환경 세팅 + 모델 캐싱
bash scripts/run_baseline.sh agent # 트레이스 생성 → 서버 기동 → 재생 → 진단

run_baseline.sh 하나가 끝까지 갑니다. 마지막에 병목 진단 리포트가 나오는데, 실제 출력은 이런 식입니다:

[5] 그룹별 캐시 적중률 (턴 / 스키마)
        그룹     건수   평균프롬프트    캐시적중   TTFT p50
         0        2        1715       0.9%      16.9
         2        2        2728      87.4%      14.8
         4        2        3970      93.7%      14.4
  => 턴이 올라가는데 적중률이 오르지 않으면 프리픽스가 evict 되고 있다.

W2 담당자는 여기서 think_mean을 올려가며 이 수치가 무너지는 걸 직접 보게 됩니다.

배점을 이렇게 잡은 이유

병목 규명 25점, 트레이드오프 25점. 성능 향상 폭 자체는 배점에 없습니다. 개선폭 0%로 끝나도 왜 안 되는지를 증거로 규명했으면 만점이 가능하고, 3배 빨라졌는데 그게 원래 radix cache 덕분이었으면 큰 감점입니다. "이미 SGLang에 있는데요?"라는 학생들의 우려도 README 2장에서 정면으로 다뤄뒀습니다.

자동 감점 항목(3-bar 누락 −15, 정확성 게이트 미실행 −15, 트레이드오프에 "손해 없음" −20)은 미리 공지하시는 게 좋습니다. 특히 마지막 건 학생들이 방어적으로 쓰려는 유혹이 강한 부분입니다.

준비하실 때 결정하셔야 할 것

SGLang 릴리스 태그를 첫 주에 확정해서 README와 setup_pod.sh에 박아 넣으세요. 문서에는 <확정된 태그>로 비워뒀습니다. 이게 안 정해지면 5주 뒤에 5명이 서로 다른 엔진을 측정한 결과를 들고 옵니다.

그리고 **2주차 중간 점검(docs/05 마지막 절의 1페이지 양식)**을 실제로 걷으세요. [3] 증거 세 칸이 다 안 차 있으면 3단계로 못 넘어가게 막는 게, 이 프로젝트에서 가장 효과가 큰 개입입니다.
