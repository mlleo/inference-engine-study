## 시나리오

문서 검색 기반 QA 서비스. 요청마다 벡터 DB 에서 청크 6개(각 약 1,200 토큰)를
검색해 프롬프트에 붙인다. 입력은 7k 토큰대, 출력은 140 토큰 내외.
인기 문서는 계속 검색된다(Zipf 분포).

```bash
python -m workloads.generators rag --out traces/ --model Qwen/Qwen3-4B
bash scripts/run_baseline.sh rag
```

## 주 병목

**Prefill 지배 + KV 용량.** 입력:출력 계산량 비가 약 50:1 이다.

## 이 워크로드의 진짜 함정

청크 **재사용률은 높은데(60%+) 캐시 적중률은 거의 0** 이다.

이유는 생성기의 `rng.shuffle(ids)` 한 줄이다. 실제 검색 시스템도 마찬가지로,
같은 청크 집합이 검색되어도 **랭킹 순서가 요청마다 달라진다.** RadixAttention 은
접두사(prefix) 트리이므로 첫 청크가 다른 순간 매칭이 끊긴다. 청크 A,B,C 와
C,A,B 는 공유 프리픽스가 시스템 프롬프트뿐이다.

**먼저 이것을 측정으로 확인하라.** `--set reuse_alpha=2.0` 으로 재사용을 극단적으로
높여도 `cache_hit_%` 가 오르지 않는 것을 보여주는 것이 1차 목표다.

## SGLang 이 이미 하는 것

- RadixAttention (접두사 KV 재사용)
- Chunked prefill (긴 prefill 을 쪼개 decode 를 굶기지 않음)
- Hierarchical cache (CPU/디스크 KV 오프로딩)

## SGLang 이 아직 못 하는 것 = 과제 후보

1. **위치 독립적 KV 재사용** — 청크별 KV 를 순서와 무관하게 재사용하고,
   청크 간 어텐션만 선택적으로 재계산. (CacheBlend / EPIC 계열 아이디어)
   난이도 높음, 임팩트 큼.
2. **비용 인지 evict 정책** — 현재는 LRU. "재계산 비용 / 바이트" 기준으로
   바꾸면 긴 청크가 우선 보존된다. 난이도 낮음, 자기 완결적.
3. **청크 경계 정렬 캐싱** — 청크 경계를 KV 블록 경계에 맞춰 부분 재사용 가능성을 높임.

## 스윕할 축

```bash
--set reuse_alpha=0.5 / 1.1 / 2.0      # 재사용 강도
--set chunks_per_req=3 / 6 / 12        # 컨텍스트 길이
--set qps=0.3 / 0.6 / 1.2 / 2.4        # 부하
```

## 확인할 서버 로그

```
token usage       KV 풀 점유율. prefill 이 몰릴 때 얼마나 차는가
cache hit rate    클라이언트 cached_tokens 와 교차 검증
#queue-req        prefill 대기 행렬
```

## 예상되는 트레이드오프 (5단계에서 확인할 것)

- 위치 독립 재사용은 **정확도를 희생**한다. 재계산할 청크 간 어텐션 비율을
  줄일수록 빨라지고 품질이 떨어진다. 이 곡선을 반드시 그려라.
- 청크별 KV 를 따로 들고 있으면 **메모리 단편화**가 생긴다.
- 짧은 요청만 오는 워크로드(W4)에서는 순수 오버헤드다.
