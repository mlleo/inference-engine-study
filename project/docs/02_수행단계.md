# 수행 5단계 상세 가이드

각 단계마다 **완료 조건(Definition of Done)** 이 있다. 그것을 만족하지 못한 채
다음 단계로 넘어가지 말 것.

## 1단계 — 워크로드 분석 (2주차 전반)

### 핵심 질문
> 이 워크로드는 **무엇이** 어려운가? 다른 워크로드와 뭐가 다른가?

### 할 일

**(a) 트레이스를 직접 열어본다.** 코드를 돌리기 전에 데이터를 본다.

```bash
python -m workloads.generators <내워크로드> --out traces/ --model Qwen/Qwen3-4B
python -m bench.replay --trace traces/<내워크로드>.jsonl --tag x --dry-run
head -3 traces/<내워크로드>.jsonl | python -m json.tool
```

**(b) 다음 표를 채운다.** 보고서 1절에 그대로 들어간다.

| 항목 | 값 | 어떻게 구했나 |
|------|-----|--------------|
| 입력 토큰 길이 분포 (p50/p90/p99) | | |
| 출력 토큰 길이 분포 (p50/p90/p99) | | |
| 입력:출력 비율 | | prefill vs decode 비중의 1차 근사 |
| 요청 간 공유 프리픽스 구조 | | 어떤 부분이 공유되고, **왜 매칭이 깨지는가** |
| 요청 도착 패턴 | | 포아송인가 버스트인가, QPS 는 |
| 세션 구조 | | 독립 요청인가, 멀티턴 연쇄인가 |
| SLO 정의 | | TTFT/TPOT 목표치와 그 근거 |
| 동시 KV 점유 최대치 추정 | | 토큰 수 × 레이어 × KV 헤드 × 2 × dtype |

**(c) "무엇이 어려운가"를 한 문단으로 쓴다.** 이 문단이 모든 것의 출발점이다.

> 나쁜 예: "요청이 많아서 느리다."
> 좋은 예: "요청당 입력이 7.4k 토큰인데 출력은 140 토큰이라 prefill:decode 계산량
> 비가 약 50:1 이다. 게다가 검색된 청크의 순서가 요청마다 달라서, 청크 재사용률이
> 60% 인데도 접두사 매칭이 첫 청크에서 끊겨 KV 재사용이 사실상 일어나지 않는다."

### 완료 조건
- 위 표가 전부 채워졌다.
- SLO 를 숫자로 정의했고 그 근거를 댈 수 있다.
- 아직 아무 코드도 수정하지 않았다.

## 2단계 — 병목 규명 (2주차 후반)

### 핵심 질문
> prefill / decode / KV 메모리 / 스케줄러 / CPU 중 **어디**인가?
> 그렇게 판단한 **증거**는 무엇인가?

### 할 일

**(a) 베이스라인을 돌리고 진단 리포트를 읽는다.**

```bash
bash scripts/run_baseline.sh <내워크로드>
python -m bench.analyze results/<내워크로드>__default.json
```

**(b) 클라이언트 지표와 서버 로그를 반드시 대조한다.**

클라이언트는 "얼마나 느린가"만 안다. 원인은 서버가 안다.
SGLang 은 매 스텝 아래를 로그로 찍는다.

| 로그 항목 | 무엇을 말해주는가 |
|-----------|-------------------|
| `#running-req` | 실제 배치 크기. 기대보다 작으면 메모리나 스케줄러 문제. |
| `token usage` | KV 풀 점유율. 1.0 근처에 붙어 있으면 메모리 압박. |
| `#queue-req` | 대기 중인 요청. 계속 증가하면 시스템 포화. |
| `cache hit rate` | radix cache 실제 적중률. 클라이언트의 `cached_tokens` 와 교차 검증. |
| `#retracted` | 메모리 부족으로 선점(preempt)된 요청 수. **0 이 아니면 그 자체가 이야기다.** |

```bash
grep -E "#running-req|token usage|#retracted|cache hit rate" logs/server_default.log | tail -40
```

**(c) ablation 으로 인과를 확정한다.** 상관이 아니라 인과여야 한다.
관련 기능을 끄고 다시 돌려서, 내가 지목한 병목이 실제로 악화되는지 본다.

```bash
# 예: radix cache 가 병목의 핵심이라고 주장한다면
python -m sglang.launch_server ... --disable-radix-cache
# -> TTFT 가 유의미하게 나빠져야 한다. 안 나빠지면 가설이 틀린 것이다.
```

**(d) 부하를 올려 붕괴 지점을 찾는다.** 여유 있는 시스템은 병목을 보여주지 않는다.

```bash
for Q in 0.5 1 2 4 8; do
  python -m workloads.generators <내워크로드> --out traces/ \
    --model Qwen/Qwen3-4B --set qps=$Q --suffix _q$Q
done
# 각각 재생 → goodput 이 꺾이는 지점(knee)이 어디인가?
```

### 완료 조건
- 병목을 한 문장으로 지목할 수 있다.
- 그 근거로 **클라이언트 지표 1개 + 서버 로그 1개 + ablation 결과 1개**를 댈 수 있다.
- 부하 스윕 곡선이 있고, goodput 이 꺾이는 지점을 안다.
- 여기까지가 2주차 발표 내용이다. **아직 코드를 짜지 않았다.**

## 3단계 — 엔진 수정 (3~4주차)

### 핵심 질문
> SGLang 이 **아직 하지 않는** 무엇을 할 것인가?

### 할 일

**(a) 범위를 좁힌다.** 최적화는 **하나**만 한다. 두 개를 동시에 넣으면 어느 쪽이
효과를 냈는지 영원히 알 수 없다.

**(b) 반드시 켜고 끌 수 있게 만든다.**

```python
# 예시: server_args.py 에 플래그 추가
parser.add_argument("--enable-session-pin", action="store_true",
                    help="[스터디] 세션 인지 프리픽스 유지")
```

플래그가 없으면 3-bar 실험이 불가능하다. 이건 선택이 아니다.

**(c) 주로 보게 될 파일들**

```
python/sglang/srt/managers/scheduler.py          스케줄 루프, 배치 구성, retraction
python/sglang/srt/managers/schedule_policy.py    요청 우선순위 정책 (LPM 등)
python/sglang/srt/managers/schedule_batch.py     배치 상태, KV 할당
python/sglang/srt/mem_cache/radix_cache.py       프리픽스 트리, evict 정책
python/sglang/srt/mem_cache/memory_pool.py       KV 풀
python/sglang/srt/server_args.py                 플래그 추가 지점
```

**(d) 자주 하는 실수**
- Python 만 수정한다. `sgl-kernel` 재빌드가 필요해지면 범위를 잘못 잡은 것이다.
- 기존 동작을 조용히 바꾸지 않는다. 플래그가 꺼져 있으면 순정과 동일해야 한다.
- 매 커밋마다 정확성 게이트를 돌린다. 마지막에 몰아서 하면 원인 추적이 지옥이 된다.

### 완료 조건
- 최적화가 플래그 하나로 켜고 꺼진다.
- 플래그 OFF 시 순정 SGLang 과 결과가 동일하다.
- `bench/verify.py` 가 PASS 한다.
- diff 가 읽을 만한 크기다 (수백 줄 이내).

## 4단계 — 평가 (4주차)

### 핵심 질문
> 공통 베이스라인 대비 **얼마나** 좋아졌는가? 그게 정말 **내 기여**인가?

### 할 일

**3-bar 프로토콜.** 상세는 [`03_실험프로토콜.md`](03_실험프로토콜.md).

```bash
MINE_FLAGS="--enable-session-pin" \
  bash scripts/run_matrix.sh traces/<내워크로드>.jsonl --disable-radix-cache
```

세 줄이 나온다.

| bar | 의미 |
|-----|------|
| `default` | 순정 SGLang. **내가 이겨야 하는 대상.** |
| `ablated` | 관련 기능만 끔. **그 기능이 이미 주고 있던 이득.** |
| `mine` | 내 수정본. |

`ablated` 를 빼면, radix cache 가 원래 내주던 3배 향상이 내 기여로 둔갑한다.
이건 이 스터디에서 가장 흔한 실수다.

**부하 스윕 곡선을 그린다.** 한 점이 아니라 곡선이어야 한다.

```bash
for Q in 0.5 1 2 4 8; do ... done
python -m bench.metrics 'results/*_q*__*.json' --csv sweep.csv
```

### 완료 조건
- 3-bar 표가 있다.
- 부하 스윕 곡선이 있다 (x축 QPS, y축 goodput 및 P99 TTFT).
- 정확성 게이트 PASS 로그가 보고서에 붙어 있다.
- 원시 `results/*.json` 을 제출했다.

## 5단계 — 트레이드오프 분석 (5주차) ★ 배점 최고

### 핵심 질문
> **무엇이 나빠졌는가?** 내 최적화는 어떤 상황에서 **지는가?**

### 할 일

**(a) 자기 최적화가 지는 워크로드를 스스로 찾아낸다.** 이게 필수 제출물이다.
찾지 못했다면 아직 충분히 찾아보지 않은 것이다. 모든 최적화에는 반드시 있다.

**(b) 5×5 교차 검증.**

```bash
MINE_FLAGS="--enable-session-pin" bash scripts/cross_replay.sh mine
```

내 엔진을 다른 4명의 워크로드에도 전부 돌린다. 5명이 각자 하면 5×5 행렬이 완성된다.
**대각선이 아닌 칸들이 이 스터디의 진짜 결과물이다.**

**(c) 비용을 명시적으로 적는다.**

| 비용 항목 | 확인 방법 |
|-----------|-----------|
| 메모리 오버헤드 | 자료구조 추가분, 사용 가능 KV 감소량 |
| CPU 오버헤드 | 스케줄러 스텝 시간, 짧은 요청의 TTFT 증가 |
| 공정성 | 손해를 보는 요청군이 있는가? `--by` 로 분해 |
| 꼬리 지연 | 평균은 좋아지고 P99 는 나빠지지 않았는가? |
| 정확성 | 근사(approximation)를 썼다면 품질 손실은? |

**(d) 언제 켜면 안 되는지를 쓴다.** 보고서의 마지막 문단은 이렇게 되어야 한다.

> "이 최적화는 [조건 A, B] 에서 X% 이득이지만, [조건 C] 에서는 Y% 손해다.
>  따라서 [C] 가 예상되는 배포 환경에서는 기본으로 켜지 말아야 한다."

### 완료 조건
- 내 최적화가 지는 워크로드를 하나 이상 **수치와 함께** 제시했다.
- 왜 지는지 메커니즘 수준으로 설명했다.
- "언제 켜지 말아야 하는가"에 답했다.
