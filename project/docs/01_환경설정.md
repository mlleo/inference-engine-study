# 환경 설정 가이드

## 1. 고정 사항 (전원 동일, 협상 불가)

| 항목 | 값 |
|------|-----|
| SGLang 버전 | 스터디 시작 시 **릴리스 태그 하나로 확정**하고 전원 동일하게 사용 |
| 모델 | `Qwen/Qwen3-4B` (bf16) |
| GPU | 24GB급 (RTX 4090 / A5000 / L4) 또는 48GB급 (A40 / L40S) |
| 컨텍스트 | `--context-length 32768` |
| 메모리 | `--mem-fraction-static 0.85` |
| 시드 | `--random-seed 42` |

SGLang `main` 은 3주면 사실상 다른 엔진이 된다. 두 사람이 3주 간격으로 측정한
결과는 같은 시스템의 결과가 아니다. **첫 주에 태그를 확정하고 README 에 박아둔다.**

모델을 4B 로 정한 이유: 24GB 카드에서 가중치 약 8GB 를 쓰고 KV 에 약 15GB 가
남는다. W1(RAG)과 W5(혼합)의 32k 컨텍스트를 감당하면서도, W3(장문 추론)에서
메모리 압박과 retraction 을 실제로 관측할 수 있는 크기다. 더 크면 비용이 오르고,
더 작으면 병목이 안 생겨서 볼 게 없다.

## 2. GPU 파드 (RunPod)

```bash
# 네트워크 볼륨을 /workspace 에 마운트한 상태에서
export HF_HOME=/workspace/hf          # <-- 중요
export SGLANG_VERSION=0.5.18
export MODEL=Qwen/Qwen3-4B
bash scripts/setup_pod.sh
```

**`HF_HOME` 을 반드시 네트워크 볼륨에 둔다.** 파드를 띄울 때마다 8GB 가중치를
다시 받는 것이, 이 스터디에서 가장 크고 가장 피하기 쉬운 낭비다.

스크립트 마지막에 출력되는 환경 정보(sglang/torch 버전, GPU 이름, 드라이버)는
**보고서 부록에 그대로 붙여넣는다.**

## 3. 로컬 (노트북, GPU 불필요)

아래는 전부 GPU 없이 돌아간다. 개발은 로컬에서 하고 파드는 측정할 때만 켠다.

```bash
pip install -r requirements.txt

python -m workloads.generators <워크로드> --out traces/   # 트레이스 생성
python -m bench.metrics 'results/*.json'                  # 지표 계산
python -m bench.analyze results/xxx__default.json         # 병목 진단
python -m bench.verify a.json b.json                      # 정확성 검증
python -m bench.replay --trace t.jsonl --tag x --dry-run  # 스케줄 확인
```

## 4. 트레이스 생성 규칙

```bash
# 제출용 (토크나이저 지정 필수 → 토큰 길이가 정확해짐)
python -m workloads.generators all --out traces/ --model Qwen/Qwen3-4B

# 파이프라인 디버깅용 축소본 (몇십 초면 끝남)
python -m workloads.generators <워크로드> --out traces/ --scale 0.05 --suffix _smoke

# 파라미터 스윕
python -m workloads.generators agent --out traces/ --set think_mean=30 --suffix _t30
```

**생성된 `traces/*.jsonl` 은 git 에 커밋한다.** 5명이 바이트 단위로 동일한
트레이스를 재생해야 비교가 성립한다.

## 5. SGLang fork 작업

```bash
git clone https://github.com/sgl-project/sglang
cd sglang && git checkout v0.5.18 && git checkout -b study/<내이름>
pip install -e "python[all]"
```

**Python 만 수정한다.** `sgl-kernel` 을 재빌드해야 하는 순간 며칠이 날아간다.
이 제약은 자연스럽게 스케줄러/캐시/정책 쪽으로 주제를 몰아주는데, 그게 이
스터디의 적정 범위다.

주로 보게 될 파일:

```
python/sglang/srt/managers/scheduler.py          스케줄 루프, 배치 구성, retraction
python/sglang/srt/managers/schedule_policy.py    요청 우선순위 (LPM 등)
python/sglang/srt/managers/schedule_batch.py     배치 상태, KV 할당
python/sglang/srt/mem_cache/radix_cache.py       프리픽스 트리, evict
python/sglang/srt/mem_cache/memory_pool.py       KV 풀
python/sglang/srt/server_args.py                 플래그 추가 지점
```

## 6. 트러블슈팅

| 증상 | 원인 / 대처 |
|------|-------------|
| 서버 기동이 오래 걸림 | CUDA graph 캡처 중. 정상. 개발 중에는 `--disable-cuda-graph` 로 단축하되 **측정 시에는 반드시 다시 켠다.** |
| CUDA OOM | `--mem-fraction-static` 을 0.80 으로 낮추거나 `--context-length` 축소. 다만 이 값은 전원 동일해야 하므로 **바꾸면 스터디 전체에 공지한다.** |
| `cached_tokens` 가 항상 0 | radix cache 가 꺼졌거나, 요청 간 공유 프리픽스가 실제로 없는 것. W1 담당자에게는 이게 버그가 아니라 **발견해야 할 현상**이다. |
| 첫 요청만 유난히 느림 | 워밍업 부족. `--warmup` 값을 늘린다. |
| 클라이언트에서 타임아웃 | 서버 포화. `--timeout` 을 늘리기 전에, **그 포화 자체가 측정 대상은 아닌지** 먼저 생각해볼 것. |
| 결과가 실행마다 크게 다름 | 다른 프로세스가 GPU 를 쓰고 있는지 `nvidia-smi` 확인. 워밍업 확인. 그래도 흔들리면 3회 반복 후 중앙값 보고. |
