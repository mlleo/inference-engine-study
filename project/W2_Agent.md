## 시나리오

툴을 쓰는 에이전트. 세션마다 6턴이 이어지고, 각 턴 사이에는 툴 실행 시간
(think time, 중앙값 8초)이 있다. 프롬프트는 턴마다 누적되어
**1.7k → 6k 토큰까지 단조 증가**한다. 툴 정의 블록은 5종뿐이라 세션 간에도
공유 프리픽스가 존재한다.

```bash
python -m workloads.generators agent --out traces/ --model Qwen/Qwen3-4B
bash scripts/run_baseline.sh agent
```

## 주 병목

**캐시 유지(retention).** 세션의 프리픽스는 계속 커지는데, think time 동안
다른 세션들이 KV 를 채워서 LRU 로 evict 된다. 다음 턴에서 6k 토큰을 통째로
다시 prefill 한다.

## 이 워크로드의 진짜 함정

**think time 은 클라이언트 지연이 아니라 서버 캐시 정책 문제다.**

턴 N+1 은 턴 N 이 완료되기 전에는 존재조차 할 수 없다. 그래서 재생 하니스는
연쇄(chained) 도착을 쓴다 — 부모가 끝난 뒤 think_time 만큼 기다렸다가 발사하고,
프롬프트는 실제로 `부모_프롬프트 + 부모_출력 + suffix` 로 조립된다.
히스토리를 가짜로 채워 넣으면 이 과제 전체가 아무것도 측정하지 못한다.

**1차 목표:** `--set think_mean=1` 부터 `60` 까지 스윕하면서 `cache_hit_%` 가
절벽처럼 떨어지는 지점을 찾아라. **그 지점이 이 시스템의 유효 캐시 보존 시간이다.**

```bash
python -m bench.metrics 'results/agent__*.json' --by turn_idx
```
턴이 올라가는데 적중률이 따라 오르지 않으면 evict 되고 있다는 뜻이다.

## SGLang 이 이미 하는 것

- RadixAttention + LRU evict
- Hierarchical cache (CPU 오프로딩)

## SGLang 이 아직 못 하는 것 = 과제 후보

1. **세션 인지 유지 정책** — 후속 턴이 예상되는 프리픽스에 보호 시간(protection
   window)을 준다. evict 우선순위를 `마지막 접근 시각` 이 아니라
   `후속 턴 확률 × 재계산 비용` 으로. 난이도 중간, 자기 완결적. **추천.**
2. **명시적 세션 핀(pin)** — API 에 session_id 를 받아 해당 프리픽스를 고정하고,
   TTL 또는 명시적 해제로 푼다. 난이도 낮음, 대신 악용 시 KV 고갈 위험을
   반드시 다뤄야 한다.
3. **선제적 CPU 오프로딩** — 턴이 끝나면 evict 대신 CPU 로 내리고, 다음 턴에
   올린다. PCIe 대역폭 vs 재계산 비용의 손익분기점을 찾는 것이 핵심.

## 스윕할 축

```bash
--set think_mean=1 / 4 / 8 / 20 / 60   # ★ 핵심 축
--set sessions=20 / 40 / 80            # 캐시 경쟁 강도
--set turns=3 / 6 / 12                 # 프리픽스 성장 폭
```

## 확인할 서버 로그

```
cache hit rate    턴 진행에 따라 올라가야 정상. 안 오르면 evict.
token usage       세션이 많을 때 KV 점유율
#running-req      think time 동안 배치가 비는가
```

## 예상되는 트레이드오프 (5단계에서 확인할 것)

- 프리픽스를 오래 붙잡으면 **다른 요청이 쓸 KV 가 줄어든다.** 세션 수를 늘리며
  이 손익분기점을 찾아라.
- 세션 핀은 **공정성 문제**를 만든다. 오래된 세션이 신규 요청을 굶긴다.
- W3(장문 추론)처럼 KV 가 부족한 워크로드에서는 순수 손해다. 교차 검증에서
  확인될 것이다.
- think time 이 짧으면(1초) 기본 LRU 로도 충분해서 **개선폭이 0 에 수렴한다.**
  이 구간을 곡선에 반드시 포함시켜라.
