# 실험 프로토콜

이 문서의 규칙을 어기고 나온 숫자는 발표에서 채택되지 않는다.

---

## 1. 3-bar 프로토콜

보고하는 **모든** 결과는 세 줄이 함께 있어야 한다.

| bar | 서버 설정 | 답하는 질문 |
|-----|-----------|-------------|
| **A. default** | 순정 SGLang, 기능 전부 켬 | 내가 이겨야 하는 기준선은 무엇인가 |
| **B. ablated** | 관련 기능만 끔 | **그 기능이 이미 주고 있던 이득은 얼마인가** |
| **C. mine** | 내 수정본 | 내 순수 기여분은 얼마인가 |

### 왜 B 가 필수인가

B 없이 A 와 C 만 비교하면, "3배 빨라졌다"가 사실은 **radix cache 가 원래 하던
일**이었다는 걸 아무도 알아채지 못한다. 이 스터디에서 가장 흔한 실수이고, 발표
때 가장 먼저 지적당하는 지점이다.

B 는 또 다른 역할을 한다. **B와 A의 간극이 작다면, 그 기능은 이 워크로드에서
별로 하는 일이 없다는 뜻이다.** 그렇다면 그 기능을 개선하는 프로젝트는 처음부터
방향이 틀렸을 가능성이 높다. B는 3단계에 들어가기 전에 방향을 교정해준다.

### 워크로드별 ablation 플래그

| 워크로드 | ablation 플래그 |
|----------|----------------|
| W1 RAG | `--disable-radix-cache` |
| W2 에이전트 | `--disable-radix-cache` |
| W3 장문 추론 | `--chunked-prefill-size -1` |
| W4 구조화 출력 | `--grammar-backend outlines` (기본 xgrammar 대비) |
| W5 혼합 SLO | `--schedule-policy fcfs` (기본 lpm 대비) |
| 공통 참고 | `--disable-cuda-graph`, `--disable-overlap-schedule` |

```bash
MINE_FLAGS="--enable-내플래그" \
  bash scripts/run_matrix.sh traces/<워크로드>.jsonl <ablation 플래그>
```

## 2. 측정 규칙

### 반드시 지킬 것

1. **워밍업.** 첫 요청에는 CUDA graph 캡처, JIT 컴파일, 가중치 페이지 폴트가
   섞여 있다. `replay.py` 가 자동으로 하지만 값이 충분한지 확인한다.
2. **매 bar 마다 서버를 재시작한다.** 이전 실험의 캐시 상태가 다음 실험에
   새어 들어가면 안 된다. `run_matrix.sh` 가 처리한다.
3. **open loop 를 유지한다.** `--max-inflight` 를 임의로 낮추지 않는다.
   큐잉은 서버가 해야지 클라이언트가 하면 안 된다.
4. **원시 결과를 보관한다.** 백분위 하나 바꾸려고 GPU 를 다시 켜는 일은 없어야 한다.
5. **동일 조건 3회.** 편차가 크면 중앙값을 보고하고 편차도 함께 적는다.

### 지표 정의

| 지표 | 정의 | 무엇을 말해주는가 |
|------|------|------------------|
| TTFT | 요청 제출 → 첫 토큰 | prefill + **큐 대기**. 이 둘이 섞여 있음에 유의. |
| TPOT | 첫 토큰 이후 토큰당 평균 시간 | decode 속도, 배치 경쟁 상황 |
| maxITL | 한 요청 내 최악의 토큰 간 정체 | 사용자가 "멈췄다"고 느끼는 순간 |
| cache_hit_% | 재사용된 프롬프트 토큰 비율 | 캐시 작업의 핵심 지표 |
| **goodput** | **SLO 를 만족한 요청 수 / 초** | **헤드라인 지표** |

### throughput 이 아니라 goodput 을 보고한다

"처리량 40% 향상"인데 P99 TTFT 가 400ms → 9s 가 되었다면 그건 개선이 아니라
회귀다. `metrics.py` 표에 `slo_%` 와 `goodput_rps` 가 항상 함께 나오는 이유다.

## 3. 정확성 게이트

**속도 향상을 믿기 전에 반드시 먼저 돌린다.**

```bash
python -m bench.verify results/<w>__default.json results/<w>__mine.json
```

캐시와 스케줄러 버그는 조용하다. 검색된 컨텍스트를 절반 흘려도, 다른 프리픽스의
KV 블록을 잘못 재사용해도, **수치는 좋아지고 출력만 미묘하게 틀린다.**

판정:

| 결과 | 해석 |
|------|------|
| 일치율 95%+, 불일치가 시퀀스 후반 | 정상. 배치 구성에 따른 부동소수점 reduction 순서 차이. |
| 특정 부분집합이 **토큰 0번부터** 갈라짐 | **버그다.** 그 부분집합이 곧 버그 리포트다. |

100% 일치를 요구하지 말고, **일치율**과 **어디서부터 갈라지는가**를 본다.

## 4. 흔한 함정

| 함정 | 왜 문제인가 | 대처 |
|------|-------------|------|
| 폐쇄 루프 클라이언트 | 서버가 느려지면 클라이언트도 느려져서 큐잉 붕괴가 감춰짐 | open loop 유지 |
| 평균만 보기 | 멀티테넌트에서 평균은 아무것도 말해주지 않음 | `--by slo_class` 로 분해 |
| 캐시 워밍 안 함 / 과하게 함 | 실행 순서에 따라 결과가 달라짐 | bar 마다 서버 재시작 |
| 부하 한 점만 측정 | 여유 있는 시스템은 병목을 안 보여줌 | QPS 스윕 곡선 |
| `ignore_eos` 를 껐다 켰다 | 출력 길이가 달라져 비교 불가 | 트레이스에 고정된 값을 쓴다 |
| 워크로드를 자기에게 유리하게 수정 | 교차 검증이 무의미해짐 | 트레이스는 커밋된 것을 그대로 |
| 두 최적화를 동시에 넣음 | 어느 쪽 효과인지 알 수 없음 | 하나씩, 각각 플래그로 |

## 5. 5×5 교차 검증 (5주차)

```bash
MINE_FLAGS="--enable-내플래그" bash scripts/cross_replay.sh mine
```

내 엔진을 **5개 워크로드 전부**에 돌린다. 5명이 각자 하면 행렬이 완성된다.

|  | W1 RAG | W2 에이전트 | W3 추론 | W4 구조화 | W5 혼합 |
|--|--------|------------|---------|-----------|---------|
| 엔진 A (W1 담당) | | | | | |
| 엔진 B (W2 담당) | | | | | |
| 엔진 C (W3 담당) | | | | | |
| 엔진 D (W4 담당) | | | | | |
| 엔진 E (W5 담당) | | | | | |

칸에는 `default` 대비 goodput 변화율(%)을 적는다.

**대각선은 당연히 좋아야 한다. 배울 것은 나머지 20칸에 있다.**
음수가 찍힌 칸들이 이 스터디의 결론, 즉 "모든 최적화는 특정 트래픽 패턴에 대한
베팅"이라는 명제의 증거다.

교차 검증은 축소 트레이스(`--scale 0.3`)로 해도 충분하다. 비용을 아낀다.
